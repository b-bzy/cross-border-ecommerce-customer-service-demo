# 跨境电商智能客服系统改造方案

> **项目定位**：Shopee 跨境电商场景化智能客服 Demo
> **版本**：v1.0
> **日期**：2026-10-01
> **公开边界**：使用独立实现、合成订单数据与抽象业务规则；不连接 Shopee 生产系统，不包含真实买家、订单、会话、内部规则或生产配置。

---

## 1. 改造目标

将当前本地的任务型对话原型，改造成一个可公开展示、可复现评测的**多语言跨境电商买家客服系统**。Demo 聚焦高频售后链路：

```text
查订单 → 查物流 → 修改地址 → 催发货 → 异常转人工
```

系统需体现以下能力：

1. 多语言及中英混合输入理解；
2. 一级轻量意图召回 + 二级 LLM 精排与槽位抽取；
3. 任务、FAQ、闲聊、人工接管的预仲裁；
4. 多轮上下文理解、订单消歧与待确认状态管理；
5. 基于 MCP 的订单、物流、售后服务统一接入；
6. 写操作的权限校验、二次确认与可审计调用；
7. 合成数据上的可复现评测和明确的性能口径。

## 2. 当前源码审计结论

### 2.1 当前源码的实际领域

当前本地源码并非跨境电商客服，也不是通用多行业客服，而是一个**车载语音 / 智能座舱任务型对话系统**。领域错配覆盖配置、Prompt、工具、测试数据和外部服务：

| 位置 | 当前内容 | 与目标的差距 |
|---|---|---|
| `config/class.txt` | 439 个导航、音乐、空调、车辆控制等意图 | 需要重建跨境电商意图体系 |
| `config/slot_intent.json` | 座位、温度、POI、歌曲等槽位 | 需要重建订单、地址、物流、退款等槽位 |
| `prompts.py` | 车载语音仲裁、改写、NLG 与闲聊 Prompt | 需要重写为电商客服策略 |
| `function_call/function.py` | 音乐、导航、车辆控制 Function Calling 工具 | 需要重建电商工具契约 |
| `mcp_core/amp_server.py` | 高德地图 MCP 服务 | 需要替换为订单、物流、售后 MCP 服务 |
| `test/data/` | 车载语音单轮、多轮测试集 | 需要创建合成跨境电商评测集 |
| `train/` | 面向旧领域的 BERT 意图和拒识模型 | 不适合作为首版多语言电商分类器 |

### 2.2 可保留与必须替换的部分

| 模块或思路 | 处理方式 | 改造方向 |
|---|---|---|
| 一级意图召回 | 保留思路，独立实现 | 为电商意图返回 Top-3 / Top-5 候选 |
| 二级 LLM 精排 | 保留思路，独立实现 | 仅在候选工具中选意图并抽取结构化槽位 |
| 多轮 Query Rewrite | 保留思路，重写 | 处理“这个订单”“第二个”“改成新地址”等指代 |
| 任务 / 闲聊仲裁 | 保留思路，重写 | 改为 TASK / FAQ / CHITCHAT / HANDOFF 四路由 |
| 会话状态缓存 | 可保留 Redis 思路 | 保存当前订单、待确认动作、语言与升级原因 |
| MCP 接入层 | 保留 MCP 模式，重写服务 | 用于订单、物流、售后等模拟业务能力 |
| 车载意图、槽位、工具 | 全部替换 | 不做批量关键词替换 |
| 地图、音乐、天气服务 | 删除 | 替换为电商合成服务 |
| 旧训练数据、旧测试集 | 删除 | 重建多语言、跨轮、异常场景测试集 |
| 旧源码文件组织 | 不直接沿用 | 使用独立、可维护的新目录结构 |

## 3. 公开与安全边界

### 3.1 公开 Demo 的边界

公开版本仅使用以下内容：

- 独立实现的服务代码；
- 合成的买家、订单、商品、地址、物流轨迹与售后工单；
- 抽象后的业务规则和公开可解释的方法论；
- 自建、脱敏的评测样本与性能结果；
- 明确标记为 Demo 的流程图、截图和演示数据。

禁止纳入公开仓库的内容：

- 真实 Shopee 订单、买家、卖家、员工或客服会话；
- 真实生产 API、Token、Key、Cookie、账户信息或内部网址；
- 未获授权的业务规则、内部文档、源代码、截图或指标；
- 能识别真实用户、客户、合作方或公司内部系统的任何材料。

### 3.2 品牌与项目表述

若未取得 Shopee 的书面公开授权，项目应表述为：

> **Shopee 跨境电商场景化智能客服 Demo**
> 基于公开业务流程与合成数据构建，不连接 Shopee 生产系统。

不应表述为：

- “Shopee 官方客服系统”；
- “Shopee 生产系统复刻”；
- “接入 Shopee 内部订单系统”；
- 无法提供验证依据的生产环境指标。

### 3.3 凭证处理

当前本地参考源码中发现了硬编码的第三方地图服务密钥。该密钥不能进入新 Demo、Git 历史、截图、日志、README 或 PDF。

处理规范：

1. 立即在对应平台轮换或撤销该密钥；
2. 新项目所有凭证只通过环境变量加载；
3. 提供 `.env.example`，只写占位符；
4. 提交前运行 secrets 扫描；
5. MCP 服务只读取最小权限凭证，Demo 优先完全不需要外部凭证。

## 4. 产品范围

### 4.1 MVP 用户与场景

**目标用户**：跨境电商买家。
**优先语言**：中文、英文、中英混合输入。
**第二阶段语言**：Bahasa Indonesia、Bahasa Melayu、Thai、Vietnamese。

**MVP 主链路**：

```text
买家输入问题
  → 识别语言与会话上下文
  → 召回候选意图
  → LLM 在候选工具中精排
  → 查询合成订单 / 物流信息
  → 对改址、催发货等写操作进行策略校验
  → 用户二次确认
  → 调用 MCP 模拟业务服务
  → 返回多语言、可解释的客服回复
```

### 4.2 一级域与意图体系

首版控制在约 16 个意图，优先保证深度和可评测性。

| 一级域 | Intent | 示例 |
|---|---|---|
| 商品咨询 | `product_search` | “Do you have this in black?” |
| 商品咨询 | `product_detail` | “这个商品的材质是什么？” |
| 商品咨询 | `size_guide` | “What size should I choose?” |
| 营销活动 | `promotion_eligibility` | “Why can’t I use this coupon?” |
| 订单服务 | `order_status` | “我的订单到哪一步了？” |
| 订单服务 | `order_cancel` | “Can I cancel order SB-10023?” |
| 订单服务 | `address_change` | “把这个订单改寄到新地址。” |
| 物流服务 | `shipment_tracking` | “Where is my parcel now?” |
| 物流服务 | `shipment_exception` | “包裹卡在 customs clearance 两天了。” |
| 物流服务 | `delivery_urge` | “可以帮我催一下发货吗？” |
| 售后服务 | `return_eligibility` | “这个商品还可以退吗？” |
| 售后服务 | `refund_status` | “退款为什么还没到账？” |
| 售后服务 | `exchange_request` | “I received the wrong size.” |
| 服务支持 | `human_handoff` | “I want to talk to a real person.” |
| 服务支持 | `complaint` | “This is unacceptable.” |
| 非任务域 | `chitchat_or_out_of_scope` | “你觉得新加坡天气怎么样？” |

## 5. 目标技术架构

```text
Buyer Web Chat / Demo UI
        │
        ▼
API Gateway
  ├─ session_id / locale / trace_id
  ├─ PII 脱敏与输入校验
  └─ 请求审计
        │
        ▼
Conversation Orchestrator
  ├─ Language Detection
  ├─ Context Resolver
  ├─ TASK / FAQ / CHITCHAT / HANDOFF Router
  ├─ Intent Recall (Top-K)
  ├─ LLM Reranker + Slot Extraction
  ├─ Policy & Confirmation Gate
  └─ Response Composer
        │
        ├───────────────┬─────────────────┬──────────────────┐
        ▼               ▼                 ▼                  ▼
Order MCP          Logistics MCP      After-sales MCP     Knowledge Base
        │
        ▼
Synthetic Commerce Data Store
```

### 5.1 分层职责

| 层级 | 职责 | 关键原则 |
|---|---|---|
| API Gateway | 接收消息、生成追踪 ID、限流、输入校验 | 不在入口层做业务决策 |
| Context Resolver | 解析当前订单、上轮意图、待确认动作 | 不凭空猜测订单或地址 |
| Router | 判定 TASK / FAQ / CHITCHAT / HANDOFF | 高风险、投诉、人工请求优先升级 |
| Intent Retriever | 召回候选意图及工具 | 快、可解释、可离线评测 |
| LLM Reranker | 在候选范围内精排、抽槽位、生成澄清问题 | 不暴露全部工具，不直接执行写操作 |
| Policy Gate | 校验订单状态、权限、必填字段、确认状态 | 后端策略优先于模型输出 |
| MCP Adapter | 调用标准化订单、物流、售后工具 | 输入输出使用严格契约 |
| Response Composer | 基于结构化工具结果生成多语言回复 | 不编造订单状态或规则 |

## 6. 两阶段意图识别方案

### 6.1 一级：轻量候选召回

目标是快速缩小候选意图范围，而非一次性完成最终决策。

```text
用户输入
  → 语言检测与文本归一化
  → 订单号 / 物流号 / 地址 / 日期等实体规则识别
  → 关键词、BM25、向量召回融合
  → 输出 Top-3 / Top-5 候选意图与得分
```

推荐融合优先级：

```text
明确实体或规则命中
  > 精确关键词匹配
  > 向量语义相似度
  > BM25 词法相似度
```

示例：

```text
输入：My order hasn’t moved for 4 days, can you speed it up?

一级候选：
1. shipment_exception
2. delivery_urge
3. shipment_tracking
```

**一级评测指标**：`Recall@3`，即真实意图是否被召回到 Top-3 中。

### 6.2 二级：LLM 精排与槽位抽取

二级模型只接收一级候选工具、当前会话状态和严格定义的工具契约。

```json
{
  "intent": "address_change",
  "confidence": 0.91,
  "order_id": "SB-10023",
  "slots": {
    "new_country": "Singapore",
    "new_address": "10 Anson Road, #12-01"
  },
  "need_confirmation": true,
  "reason_code": "WRITE_OPERATION"
}
```

关键约束：

1. 模型只负责理解、精排和抽取，不能直接改写订单；
2. 模型只能从一级候选工具中选择；
3. 所有输出必须经 JSON Schema / Pydantic 校验；
4. 必填槽位缺失时必须澄清，不能猜测；
5. 多订单场景必须先让用户选择；
6. 写操作必须由 Policy Gate 决定是否可执行。

## 7. 多轮状态与操作安全

### 7.1 会话状态模型

```json
{
  "session_id": "demo-session-001",
  "locale": "en-SG",
  "active_order_id": "SB-10023",
  "last_intent": "shipment_tracking",
  "pending_action": "address_change",
  "pending_confirmation": {
    "tool": "request_address_change",
    "order_id": "SB-10023"
  },
  "handoff_reason": null
}
```

建议设置合理 TTL，且不长期保存完整原始对话。Demo 日志应默认脱敏。

### 7.2 写操作二次确认

以下操作必须二次确认：

- 修改收货地址；
- 取消订单；
- 创建催发货工单；
- 发起退货 / 换货 / 退款申请；
- 创建人工升级工单。

示例：

```text
用户：把这个订单改寄到新加坡的新地址。
系统：订单 SB-10023 当前仍可修改地址。将改为：
      10 Anson Road, #12-01, Singapore。确认提交吗？
用户：确认。
系统：已提交地址修改请求，订单状态更新后会同步通知。
```

### 7.3 关键防误触发规则

| 输入或状态 | 正确处理方式 |
|---|---|
| “物流太慢了，烦死了” | 识别为抱怨，询问是否需要查物流或创建催发货工单 |
| “帮我催一下”且有当前订单 | 进入催发货确认流程 |
| “帮我催一下”但无订单上下文 | 索取订单号或展示可选订单 |
| “我不要了” | 先判断订单状态与退货资格，不直接取消 |
| “地址改成这个” | 补全地址并二次确认 |
| “我要真人客服” | 立即进入人工接管流程，不强行继续自动化任务 |
| 欺诈、账号安全、严重投诉 | 优先升级人工并返回安全指引 |

## 8. MCP 工具设计

### 8.1 MCP 的作用

MCP 用于统一 Agent 与模拟业务服务之间的工具契约、参数校验、日志与权限边界，不是为了展示技术名词而存在。

### 8.2 工具清单

```text
get_order_summary(order_id)
get_order_items(order_id)
get_shipment_tracking(order_id)
check_address_change_eligibility(order_id)
request_address_change(order_id, new_address)
create_delivery_urge_ticket(order_id, reason)
get_return_refund_status(order_id)
search_policy_knowledge(query, locale)
create_human_handoff_ticket(order_id, category, summary)
```

### 8.3 权限分层

| 工具类型 | 示例 | 调用规则 |
|---|---|---|
| 只读 | 查订单、查物流、查退款状态 | 可在订单身份和参数有效时直接调用 |
| 条件写入 | 改地址、催发货 | 校验订单状态、参数完整性并要求用户确认 |
| 人工接管 | 投诉、风险、人工请求 | 可直接创建工单，但需返回升级原因 |
| 知识问答 | 规则、时效、常见问题 | 仅基于受控合成知识库回答 |

## 9. 评测与性能口径

### 9.1 必须独立评估的指标

| 指标 | 定义 |
|---|---|
| `Recall@3` | 一级召回 Top-3 是否包含真实意图 |
| Intent Accuracy | 二级最终意图是否正确 |
| Tool Selection Accuracy | 是否选择正确业务工具 |
| Slot Exact Match | 必填槽位是否全部准确 |
| Multi-turn Success Rate | 多轮任务是否完成预期业务目标 |
| Wrong-action Rate | 是否尝试执行错误写操作 |
| Handoff Precision | 需人工升级的场景是否正确升级 |
| P95 Latency | 端到端响应延迟 |
| Tool Failure Recovery Rate | 工具异常时是否正确澄清、降级或转人工 |

### 9.2 数据集规范

评测集应至少覆盖：

- 中文、英文、中英混输；
- 每个意图的同义表达、口语表达、拼写错误；
- 订单号、物流号、地址等实体抽取；
- 跨轮指代与订单切换；
- 情绪表达与闲聊干扰；
- 高风险操作与拒绝场景；
- 工具失败、服务超时、订单不存在等异常。

训练、验证、测试集必须分离，不能用完全相同的模板改写后同时出现在训练和测试中。

### 9.3 指标与简历口径

“一级召回 98%、二级精准匹配 87%、QPS 200+”只有在新跨境电商测试集、冻结评测脚本和明确压测配置下复测成功后才能保留。

若尚未完成复测，建议公开材料先写为：

> 设计并实现一级轻量召回 + 二级 LLM 精排方案；基于合成多语言测试集建立 Recall@K、意图准确率、槽位准确率和多轮任务成功率评测框架。

性能需区分：

```text
Gateway QPS：仅网关、路由和模拟工具调用
Tool QPS：仅订单 / 物流 MCP 服务
E2E QPS：包含模型与工具调用的完整请求
```

报告时必须说明机器配置、并发数、模型是否 mock、样本规模、P50 / P95 延迟和错误率。

## 12. 项目最终叙事

该项目应被呈现为：

> 面向跨境电商买家服务场景，设计并实现多语言任务型智能客服 Demo。系统采用“一级轻量召回 + 二级 LLM 精排”进行受控意图路由，并以 MCP 统一接入合成订单、物流和售后服务；通过多轮状态管理、写操作确认、误落域治理和人工接管机制，完成订单查询、地址修改和催发货等关键服务链路。

这套叙事的重点不是“复刻某个平台的生产系统”，而是清晰展示：

- 产品问题定义；
- 对话系统架构设计；
- 受控 Agent 与 MCP 工具编排；
- 多语言、多轮对话与风险治理；
- 可复现工程实现与可信评测；
- 数据、版权、隐私和公开边界意识。
